### 1.3 🔴 The reporter stamps a build name that nothing else uses

Every boot-error row carries `app_version` = `16719h5` or `myjgkn`. Those are not builds — they are
SvelteKit's **djb2 hash** of the version name, read out of the `__sveltekit_<hash>` global, which is
the only build identity readable when the bundle that would have told you never loaded. Clever, and
deliberate. But nothing translates it back. I verified the mapping locally with the repository's own
hash function (<File path="site/scripts/check-build-version.mjs" line="74" />):

| Stored in `client_logs` | Actual build |
|---|---|
| `nrqdqc` | `b4b47e55…` (never seen — the reporter did not exist yet) |
| `16719h5` | `ec9d8d9c…` |
| `myjgkn` | `34fe97ec…-20260806155506` |

Consequences, all verified in <File path="site/src/lib/db/server/log-analytics.ts" line="1517" /> and
line 2292:

1. The **current-versus-stale error split** counts a row as stale when `app_version <> current`. Every
   boot-error row fails that comparison forever — so all 25 of today's blank boots, **all of which
   happened on the build that was current at the time**, are filed as *stale-build* errors. That is
   precisely the number `34fe97ec` was shipped this afternoon to make honest.
2. The **errors-by-build panel** grows two permanent phantom builds.
3. The **build-adoption / stranded-tab panel** decodes age from `app_version` or its first sighting;
   these two names will look like builds nobody ever migrated off.

**Fix (small):** translate at ingest. `insert_client_log` knows the server's own `version`; compute
`djb2(version)` once at module load and, when an incoming `app_version` equals it, store the real
version instead. Keep the hash in `context.version_hash` so a *stale* tab's unresolvable hash is
still visible and obviously not a build name. Roughly four lines plus the existing `djb2`.

consult `navigator.onLine`, and — best of all — issue one `HEAD` against the URL before declaring the
file deleted. A `200` means network; a `404` means stale. One request settles what a comment cannot.

### 1.5 🟠 A photo upload died at the edge, and the server never knew

At 19:51:54 a signed-in contributor working on `iipay-aa` uploaded a 4.75 MB JPEG and got
`Failed to upload file (status 524)`. HTTP 524 is Cloudflare's own "the origin did not answer within
100 seconds". Two of her photos had gone through fine three minutes earlier.

What we can say: the box was idle (2.5–3.1% processor, worst event-loop stall in that five-minute
window **63 ms**), so the origin was not blocked. What we cannot say: anything else — because
<File path="site/src/routes/api/photo-upload/+server.ts" line="98" /> logs only the R2 store *error*
path. There is no start event, no duration, no success event, and no timeout on the storage write. A
request that hangs for 100 seconds inside `store_media_bytes` leaves **zero** server rows, which is
exactly what happened: nothing between `dict_changes_pushed` at 19:48:45 and the next unrelated row.

Two things worth doing, in one pass: a `photo_upload_completed` event with `bytes`, `duration_ms` and
`stage` timings, and a timeout (say 45 s) on the storage write so the user gets a real error instead
of the edge's guess. Note the uptime probe measured **15.0 s to first byte at 19:54:45** — same
neighbourhood, same unattributable shape as §1.8.
