### 1.1 🔴 One commit, two builds, one name — and three instruments go blind

**What happened.** The site was rebuilt and restarted today at 14:42 UTC. No new code was committed
(the newest commit is `b4b47e55`, from 14:10 yesterday), so the version stamp the application
reports about itself — `app_version` — is the *same string* before and after. But the actual files
changed. Here is the same page bundle, before and after:

| | Before 14:40 | After 14:40 |
|---|---|---|
| Version the app reports | `b4b47e55ac6c…` | `b4b47e55ac6c…` (identical) |
| File it asks for | `/_app/immutable/nodes/9.BAi3kkdi.js` | `/_app/immutable/nodes/9.CsDktvmt.js` |
| Present on the servers now? | **No** — 404 | Yes (both containers) |

I confirmed this directly on the production machine: both `sveltekit_blue` and `sveltekit_green`
contain only `nodes/9.CsDktvmt.js`, and nothing named `9.BAi3kkdi.js`.

**Why two builds of one commit differ.** The image build deliberately reaches out to the *still-running*
site and bakes its answers into the bundle — the translated interface strings
(`site/scripts/fetch-baked-i18n.mjs`) and the homepage statistics and featured word cards
(`site/scripts/fetch-homepage-baked.mjs`), both invoked from <File path="Dockerfile" line="46" />.
Those answers change between builds, so the bundle's contents change, so every content-addressed
file name changes. Meanwhile the name the build gives *itself* is the commit identifier, fixed at
<File path="site/svelte.config.js" line="55" /> (`resolve_version_name()`).

That file's long comment is correct about the danger it was written for — the version name must be
**constant within a build**, or the page shell and the client bundle disagree and every route serves
a blank page (the nine-hour poly.education outage of 2026-08-03). It simply never claims the other
half — that the name must also be **distinct between builds** — and today is the first day that
mattered.

**What breaks, concretely.**

1. **The browser's own update check can never fire.** SvelteKit polls for a version change every 60
   seconds (`pollInterval: 60_000`, <File path="site/svelte.config.js" line="122" />). Today's
   rebuild published the same version name, so no tab anywhere learned that a new build existed.
2. **The dashboard's "stale build" error split miscounts.** <File path="site/src/lib/db/server/log-analytics.ts" line="1517" />
   counts an error as stale when `app_version <> current_app_version`. Today's thirteen
   deleted-file errors all carry the *current* version, so they were counted as **current-build
   errors** — exactly the number that is supposed to mean "the build we just shipped is broken".
3. **Today's deploy is invisible on the deploy timeline.** The markers come from the first day each
   distinct `app_version` is seen (<File path="site/src/lib/db/server/log-analytics.ts" line="303" />).
   I queried it: eight distinct versions since Aug 2, the newest first seen on **Aug 4**. There is no
   Aug 5 marker, though a deploy happened.

**The fix.** Keep the within-build guarantee and add a between-build one: have `deploy.sh` export a
build identifier alongside `GIT_SHA` (its own timestamp is enough) and make the version name
`${GIT_SHA}-${BUILD_ID}`. It is still one constant string for the whole build — every guard in
`svelte.config.js` and `check-build-version.mjs` still holds — but two builds of one commit can no
longer collide. Everything downstream (the poll, the stale split, the deploy markers, the
stale-bundle telemetry) starts telling the truth for free.

### 1.2 🔴 The immutable-asset archive shipped — and, by construction, could not have helped today

Last night's top item is **built and live**. The deploy script now extracts `_app/immutable` from the
newly built image into `/opt/hosting/immutable-archive` (<File path="/opt/hosting/sveltekit/deploy.sh" line="172" />
on the server), and Caddy serves that directory *first* for `/_app/immutable/*`, falling through to
the application only on a miss:

```
handle /_app/immutable/* {
  root * /srv/immutable-archive
  @archived file
  handle @archived {
    header Cache-Control "public, max-age=31536000, immutable"
    header X-Immutable-Archive hit
    file_server { precompressed br gzip }
  }
  handle { reverse_proxy sveltekit_blue:3000 sveltekit_green:3000 { … } }
}
```

The ledger records the first run: `{"at":"2026-08-05T14:41:53Z","retention_days":30,"files":1706,"mb":22}`.

**But it archived the build it was shipping, not the build it was replacing.** I checked every file
name that failed for a real person today against the archive:

| File a person's browser asked for | In the archive? |
|---|---|
| `nodes/9.BAi3kkdi.js` | ❌ missing |
| `nodes/12.BHXXOip6.js` | ❌ missing |
| `nodes/17.C1JgRM2T.js` | ❌ missing |
| `nodes/5.DUSIDmqS.js` | ❌ missing |
| `chunks/B_MCToPa2.js` | ❌ missing |

This is a **one-time bootstrap gap, not a defect**: the copy is additive, so from the *next* deploy
onward the archive will still hold today's files while serving tomorrow's, and coverage becomes real
(30-day retention). Nobody should read today's five failures as "the fix didn't work."

**One change would have closed even the bootstrap gap, and is worth making anyway:** copy from the
**currently running container** as well as from the new image, immediately before the swap. It costs
one extra `docker cp` and it makes the archive correct on its very first run and after any manual
`docker compose up` that bypasses a normal deploy.

**Verification for the next reviewer:** after the next deploy, request a *previous* build's asset and
confirm the response carries `X-Immutable-Archive: hit`. (Requesting through
`livingdictionaries.app` will usually hit Cloudflare's own cache instead — check the header from the
origin, or pick an asset Cloudflare has not seen.)

### 1.3 🟠 Two people in Vietnam were told "the app needs updating" because one file did not arrive

Four rows, two sessions, both from Vietnam, both anonymous, both on the **current** build:

| Time (UTC) | Event | Dictionary | Version |
|---|---|---|---|
| 12:59:21 | `stale_bundle_reload` then `stale_bundle_reload_gave_up` | `south-saami` | `b4b47e55…` (current) |
| 19:13:25 | `stale_bundle_reload` then `stale_bundle_reload_gave_up` | `nasa-yuwe-páez` | `b4b47e55…` (current) |

Both carry `boot_message: "leader worker script failed to load"` and `reason: "missing_build_artifact"`.
The standing rule from 2026-07-31 says a `_gave_up` row is a real person stuck on a stale bundle and
must always be escalated — so I escalated it, and it turns out not to be a stale bundle at all.

**The code labels this case without looking.** In <File path="site/src/lib/db/dict-client/worker/db-client.ts" line="134" />:

```js
spawned.onerror = (event) => {
  const message = (event as ErrorEvent)?.message || 'leader worker script failed to load'
  handle_boot_failure({ message, terminal_reason: boot_failure_terminal_reason?.({ message }) ?? 'missing_build_artifact' })
}
```

The comment above it explains the reasoning: *"The URL is a content-hashed `/_app/immutable/*` chunk,
so a failure to load it is the deleted-build-artifact case BY CONSTRUCTION — no message sniffing
needed."* That is true for a 404. It is **not** true for a connection that was dropped, throttled or
filtered — which produces exactly the same bare `error` event on the Worker object.

Note the asymmetry: the pure classifier next door, <File path="site/src/lib/db/client/stale-build-artifact.ts" line="63" />,
takes this seriously — it *vetoes* the classification when `online` is false, with a comment saying
so. This path never consults `online` at all.

**Proof it was not a deleted file.** The recovery ladder reloaded the page once. A reload onto a
newer build is the entire cure for a deleted asset — but each tab came back on the *same* version and
failed identically, which is precisely the condition the code's own comment calls *"the current build
is not what this tab is being served."* And the worker file the current build asks for
(`workers/leader-worker-BCVD4NBb.js`) is present on both containers and in the archive. Nothing was
deleted. One file did not arrive.

The user-visible cost is a toast reading "app update needed" with a Reload button that cannot help,
on a connection that needed a retry.

**Fix:** capture the failing script URL from the error event (today the row cannot name the file it
could not load), and consult `navigator.onLine` before classifying — the same veto the pure
classifier already applies. Better still, on failure issue one `HEAD` for the URL: a 404 proves
"deleted", anything else proves "unreachable", and the two deserve different words to the user.

### 1.4 🟠 `audio_play_failed` still cannot tell a wrong file from a file that never arrived

| Rows | Dictionary / path shape | Browser's complaint | What the file actually does |
|---|---|---|---|
| 4 | `audio/miskitu/…_1615430966024.mpeg` | `NotSupportedError`, media error 4 | **Genuinely 404** — the legacy path shape the July 23 repair cannot match. Carried item, confirmed. |
| 2 | `apatani/audio/….mp3` (Windows Chrome, India) | `NotSupportedError`, media error 4, `networkState: 3` | **File is fine.** It returns 200 with `content-type: audio/mpeg`, and decodes as a valid 0.97-second, 164 kbit/s MP3. Its playback derivative `…_p1.mp3` exists and returns 200 too. The bytes never reached the browser. |
| 6 | `tutelo-saponi/audio/….wav` (one iPhone, iOS 18.7) | `AbortError`, `networkState: 2`, `readyState: 0` | Six taps, six times nothing played, over 44 minutes. The file is a valid 512 KB WAV that returns 200. |

The middle row is the important one. India's average time-to-first-byte today was 2,174 ms (§3), and
that client got a codec complaint about a perfectly good MP3. This is the *same misdiagnosis shape as
§1.3*: an opaque browser error being labelled with its most-likely-in-Boston cause.

The six `AbortError` rows deserve a second look too. The standing 2026-07-28 ruling says an
`AbortError` meaning *"play() was interrupted by pause()"* is expected tap-and-close behaviour and
should not warn. These are not that — `networkState: 2` with `readyState: 0` means the media was
**still loading and had nothing yet**. That is a person tapping play and getting silence, six times.

**Fix:** on failure, issue one `HEAD` against the URL and record `probe_status` on the row. A 404
separates instantly from a 200, and the third case (a 200 that still would not play) becomes the only
one that needs a human. This is the 2026-07-26 enrich-first rule applied to a row that today cannot
name what failed.

sync failures** and 5 "Failed to fetch" errors, all inside this window (§2.1).

**Fix (small, high value):** give the uptime probe a second leg that bypasses Cloudflare — request
the origin directly (by IP with a `Host` header, or via an origin-only hostname) on the same
schedule. Two legs turn an ambiguous outage into a one-line answer: *both* failed = we are down;
*only the Cloudflare leg* failed = the edge is. See §5.
