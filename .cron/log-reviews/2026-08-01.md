### 1.1 🔴 The daily maintenance job blocks the site, and tonight it cost two editors their sync

At **10:30:00.756 UTC** (03:30 Pacific — the hour deliberately chosen as the quietest) the
`log-retention` cron began its daily sweep: roll yesterday's rows into the forever daily metrics,
compute the true monthly unique-visitor union, archive rows past the hot window, prune the archive,
and conditionally `VACUUM` both log files. All of it runs **synchronously, in the same Node process
that serves every request.**

I can time it exactly, without any new instrumentation, because the sweep's last act is to fork the
analytics child, and that child reports its own duration:

| Marker | Time |
|---|---|
| Sweep starts (`db_metadata.log_retention_ran_at`) | 10:30:00.756Z |
| Analytics child spawned = sweep ends (10:34:08.285Z event minus its 132,343 ms) | ≈10:31:56Z |
| **Time the request thread was blocked** | **≈115 seconds** |

And here is what the reverse proxy saw during those same 115 seconds — six connections to the
application killed mid-flight:

```
10:31:19  read tcp …->172.18.0.3:3000: read: connection reset by peer   (×2)
10:31:45  read tcp …->172.18.0.3:3000: read: connection reset by peer   (×3)
10:32:13  read tcp …->172.18.0.3:3000: read: connection reset by peer   (×1)
```

Two of those were real people. At 10:32:13 two signed-in users' dictionary sync requests came back
HTTP 502 — one working on `haidalanguage`, one on `bhutia-the-drenjongke`.

**Why a blocked thread produces resets rather than just slowness:** while the event loop is stuck
inside a single-threaded SQLite operation, nothing accepts new connections. The kernel's accept
queue fills and then starts refusing — which is precisely the `connection reset by peer` above. The
same mechanism explains why this is invisible to our synthetic prober: it samples every 5 minutes
and it happened to miss the window, so tonight's availability panel reads **270 of 270 probes OK,
100% available** on a night when two users were served errors. That is the 2026-07-27 standing
ruling about short outages, demonstrated again.

There was **no deploy** at that time (today's deploys landed at 03:20 and 11:16 UTC), so by the
standing 2026-07-30 rule — *treat any 5xx outside a deploy window as a new incident* — this is an
incident. What makes it worth a P1 is that it is **scheduled**: it will happen again at 03:30
Pacific tomorrow, and the day a `VACUUM` triggers on the 2.0 GB `logs.db` it will be much longer
than 115 seconds.

It is also the last known violation of the standing law of 2026-07-27 (*analytics and telemetry must
never block a request path*). The heavy **analytics compute** moved into a niced child process on
07-30; the **sweep that runs just before it** never did.

<Callout type="warn" title="A smaller, unprovable sibling at 00:00 UTC">
At 00:00:12 the proxy logged two more resets and one signed-in user got a 502 — again with no deploy
anywhere near. The 15-minute WAL-checkpoint cron is the natural suspect (it deliberately waits for
readers to clear, and its own comment notes that a checkpoint costs time proportional to the WAL it
drains), but it emits telemetry **only when a checkpoint fails to complete**, and tonight there were
zero such rows. So this one cannot be proven either way — which is itself the argument for the
timing telemetry in §5.
</Callout>

**Action:** instrument, then move it off the request thread — details and a staged plan in
<File path=".issues/retention-sweep-blocks-request-thread.md" />. house and tutor run the ported
copy of this same cron; broadcast when it's fixed.

### 1.2 🟠 A duplicate entry id blanked a visitor's search results

08:23 UTC, an anonymous visitor browsing `birhor` filtered to semantic domain 2 and paged through to
page 5. Two `entries_view_render_failed` rows say what happened:

```
dict_id: "birhor"   view: "list"   entry_count: 16
error: "https://svelte.dev/e/each_key_duplicate"
```

Two of those 16 entries shared an id, so Svelte refused to render the keyed list. The defensive
boundary around the results caught the throw — that guard did its job, and this is legible instead
of a white screen — but a caught boundary renders **nothing**. The visitor saw an empty results
area, with no message, on a page that should have had 16 words. Their breadcrumb trail (entry
clicks, "Show More", pages 2 → 10 → 11) is an engaged person, not a crawler.

The interesting part is that we already solved this once. The entry *page's* child lists — senses,
audio, photos, videos, sentences, related entries — all pass through a de-duplicating helper that
also emits a warning naming the offending list. The entries *results list* was never covered, in any
of its three views (list, table, gallery), even though the comment above the boundary in
`View.svelte` refers to that very helper.

The duplicate almost certainly comes from the browser-local search index rather than from server
data, which is exactly why the fix belongs at the render boundary regardless of origin. Filed as
<File path=".issues/entries-list-duplicate-key-blank-results.md" /> — de-dupe once, warn with the
duplicated id, keep the boundary as backstop.

### 1.3 🟡 Every "Internal Error" tonight came from the browser — and now we can prove it

This morning's commit added the missing client-side error hook and an `error_id` join key on the
server side. Tonight is its first production evidence, and it is decisive.

Eight crash rows in the window. The six that landed **before** the 11:16 UTC deploy carry what they
always did — a status, a URL, and nothing else:

```json
{ "status": 500, "url": ".../jejueo/entry/ec0de8b2…", "breadcrumbs": [] }
```

The two that landed **after** it carry the cause:

```json
{ "status": 500, "url": ".../birhor/entry/XiNIFVCgh7GBp30o7yY6",
  "cause": "Failed to fetch dynamically imported module: /_app/immutable/nodes/12.ZkRku0M2.js",
  "error_id": null, "origin": "client" }
```

`origin: "client"` with `error_id: null` means: SvelteKit's browser-side load/render path threw, no
server request was involved, and the thing it could not load was a content-hashed build file that a
deploy had deleted. A stale tab, in other words — the same family as §1.4, arriving through the
routing layer instead of the database layer.

That settles the 2026-07-31 finding that "zero server-side crash rows have ever been written": there
were none to write. It also means **the last several months of unexplained `Internal Error` rows
were almost certainly all stale-bundle navigations**, not server faults.

What remains open is what the *person* sees. A stale-bundle navigation lands on the generic error
page — "We ran into an error, it has been recorded, please explain what you were doing" plus a
contact button — when the honest and useful message is *"The app updated while this tab was open;
reload to continue."* The classifier that recognises this exact family already exists
(`$lib/db/client/stale-build-artifact.ts`) and the cause string is already in hand on that page.

<Callout type="info" title="Deliberately NOT a second auto-reload mechanism">
The reload-once rule lives in the data layer, and the standing instruction is that the client error
hook only *labels* a stale-build fault — it must never grow its own recovery. What's proposed here
is copy plus a reload button on the error page: a human-initiated action, not a second automatic
mechanism, and therefore compatible with both the 2026-07-09 no-forced-reload ruling and the
data-layer boundary.
</Callout>
