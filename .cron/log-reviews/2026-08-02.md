### 1.1 🔴→🟠 The maintenance sweep no longer runs on the request thread — but it still stops it, from the outside

**This is the top item and it is a genuine, measured improvement that is not yet finished.**

Last night this lane measured the daily retention sweep blocking the serving process for ~115 seconds,
producing six proxy connection resets and two signed-in users' HTTP 502s. Tonight's build runs that
sweep inside the same `nice -19` child process that computes the analytics checkpoint. What the logs
say about the result:

| | 2026-08-01 (before) | 2026-08-02 (after) |
|---|---|---|
| Blocking work on the serving thread | ~115 s | **8.3 s, once** |
| Proxy connection resets | 6 | **0** |
| Signed-in users served a 5xx in the window | 2 | **1** |
| Sweep telemetry available afterwards | none (reconstructed by hand from a proxy log) | `log_retention_swept` with **per-step wall clock** |

The sweep itself is now fully legible for the first time:

```
log_retention_swept  reason: "cron"  duration_ms: 83,306   days_rolled: 2   archived: 69,611   pruned: 0
step_ms: { list_hot_days: 3,012 · rollup_day: 15,428 · rollup_recent_months: 4,293 ·
           archive_old_logs: 20,560 · vacuum_logs_db: 39,977 }
```

**The residual mechanism, stated precisely.** The child holds SQLite write locks that the *serving*
process still waits on, synchronously, because `better-sqlite3` has no other mode:

- `rollup_day` writes `log_daily_metrics` + `log_daily_sessions` for a whole day **inside a single
  transaction** (`log-retention-cron.ts:311` `write_all`), and it ran for **15.4 seconds** across two
  days. For that whole time it owns `shared.db`'s write lock.
- The serving process opens `shared.db` with `busy_timeout = 5000` (`shared-db.ts:24`). Any request
  that writes `shared.db` during the rollup parks the event loop for up to five seconds and then
  fails.
- That is what the new meter caught: the 5-minute sample covering the sweep reported
  **`loop_lag_max_ms: 8,321`** against a **`loop_lag_p99_ms` of 12.5 ms** — i.e. one or two long
  stalls, not general slowness. And at **10:31:30**, seven seconds before the sweep finished, a
  signed-in user (`dsuslak@iu.edu`, dictionary `ayook`) got a Cloudflare 502 on a sync request.
- `logs.db` was already protected by last night's change — the serving process's busy timeout there
  is 250 ms — which is why the 40-second `VACUUM` cost nothing visible. **`shared.db` never got the
  same treatment.**

**Recommended fix (do not just copy the 250 ms trick).** Dropping `shared.db`'s serving busy timeout
would convert waits into user-visible errors on a database that carries real request-path writes. The
correct shape is to stop the child from holding the lock for seconds at a time: **chunk `write_all`
into batches** (e.g. 500 rows per transaction, with the whole-day `DELETE` in its own short
transaction), so the longest single lock hold is milliseconds. Add `ionice -c 3` to the child while
there — the two longest steps (`archive_old_logs` 20.6 s, `vacuum_logs_db` 40.0 s) are pure disk on a
two-core box, and `nice` governs CPU only.

Tracked in <File path=".issues/retention-sweep-blocks-request-thread.md" /> — reopen it with this
residual rather than filing a new one.

**Two distinct things are still missing, and neither is a mystery:**

1. **No failure surface.** `dict-session.ts:128` logs `dict_boot_recovery_exhausted` and that is the
   end of it — `dict-boot-progress.svelte.ts` has stages but no failed state, so the visitor watches
   an indeterminate bar forever. The reload-once rule (2026-07-31) correctly *declines* these: they
   are storage faults, not deleted build artifacts, and a reload cannot fix them. That makes the human
   message the only remaining lever.
2. **No cross-election bound.** The give-up ladder is bounded *within* a worker (`attempt` 0→1→2), but
   a worker re-election restarts the ladder from zero, which is how one session reaches 17 rows. This
   is the 2026-07-27 "bound the give-up path" item, now on its fourth sighting.

Both belong to <File path=".issues/dict-boot-persistent-opfs-recovery.md" /> — the open iOS checkbox.
Nothing here is new *mechanism*; what is new is that it now has a nine-and-a-half-minute human cost
attached to it, on a real public dictionary, on the current build.
