## 5. Coverage gaps (Phase B)

Verified against current source; already-covered paths (authentication, uploads, imports, sync
pushes, agent writes, share-card outcomes, host sampling) are excluded.

1. **Dashboard compute cost is now invisible — the event only fires on the path we deliberately
   emptied.** `admin_analytics_computed` is emitted in exactly one place,
   <File path="site/src/routes/api/admin/analytics/+server.ts" line="44" />, i.e. only when an admin's
   own request has to compute. Since the July 27 change moved computation to boot warm-up and the
   post-retention-sweep hook, essentially every compute now happens there and emits **nothing**: the
   persisted cache files were rewritten at 17:26 UTC today, yet the newest event in the logs is from
   **July 25**. Recommend emitting the same event (with its per-stage timing map and a
   `trigger: "warm" | "request"` field) from `warm_analytics_caches`, so compute cost stays a trend.
   *Level: info. Fields: duration, days, audience, scope, stages, trigger.*
2. **Unhandled `TypeError: Failed to fetch` rejections carry no request address.** Fifty-four rows
   tonight say only "Failed to fetch"; the page address is recorded, the *request* address is not, so
   nobody can tell whether a sync, a media file, a code chunk or a third-party call failed. The
   shared request helpers already name their route in their console message; the gap is raw `fetch`
   call sites plus the global rejection handler. Recommend stamping the attempted URL (and method)
   onto the rejection context. *Level: unchanged. Fields: url, method, page route.*
3. **Legacy media addresses deserve one counted signal, not just per-play warnings.** Tonight's
   diagnosis needed four manual checks to establish that failing audio is a stale client path rather
   than lost media. A single client-side check — "the address I am about to play does not match this
   dictionary's canonical pattern" — emitted once per session as a counted warning would make the
   remaining stale-client population measurable while the repair migration rolls out.
   *Level: warn. Fields: dictionary, media type, path shape, count.*

## 6. Dashboard improvements (Phase C + D)

### Phase C — one new proposal, grounded in tonight's evidence

**Share-card subsystem health line on `/admin/health`.** Verified absent: neither
`log-analytics.ts` nor either admin page references any share-card event. Yet this subsystem took
the whole site down five times on July 27 and has been failing **100%** of its work for nine hours
today without anything on either dashboard changing. A single aggregate line — *cards rendered
today, success rate as a percentage of attempts, requests shed, worker deaths/timeouts, and the age
of the newest stored card* — is exactly the "is this subsystem working for everyone" instrument the
standing rule asks for, and it deliberately lists no individual errors. All five inputs already
exist as events. Filed to <File path=".issues/future/dashboard-improvements.md" />.

The best *already-ready* backlog item remains the **provisional-day marker** on daily charts (the
newest point overstates by ~18% until finalization), now doubly evidenced: tonight the live tail and
the finalized rollup disagree on July 25 exactly as recorded.

### Phase D — sibling apps

- **Accepted (inbound, house 2026-07-28): "suppress or sample high-volume success telemetry."**
  House found bot-only success events doubling its hot-log volume to 262,620 rows/day. Living
  Dictionaries has the identical disease from a different source — 72,206 share-card server rows
  today, 79% of all rows. The coalescing work already written locally is the right shape; this
  confirms it should ship, not be reverted as over-engineering.
- **Declined with evidence (inbound, house 2026-07-28): "readiness is not isolation — a standby
  container doing heavy reads can slow the active one."** Checked in Living Dictionaries source:
  the analytics warm-up, retention cron, snapshot builder and checkpoint cron are all gated on
  `IS_STANDBY !== 'true'` (<File path="site/src/hooks.server.ts" line="54" />), so the standby
  performs no heavy scheduled reads. Nothing to port.
- **Already in the backlog, no duplicate:** tutor's sync-liveness strip (read the success side of
  syncing, not only failures) and house's provisional-current-day marker.
- **Not applicable:** tutor's mobile JavaScript-thread and memory panels; house's revenue work.
- **★ Outbound to house and tutor — a lesson both are one step away from repeating.** When you move
  expensive work off the request path (all three apps did this in the last three days), any telemetry
  that fires *only on the request path* goes silent at the same moment — you lose the measurement
  precisely when the optimisation lands. Living Dictionaries has been blind to its own dashboard
  compute cost since July 25 for exactly this reason. Emit the cost event from the warm/background
  path too, with a field naming the trigger.
