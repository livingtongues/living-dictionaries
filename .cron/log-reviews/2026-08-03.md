- On **2026-07-03**, the last full day before the break, Google carried **34 of 41 logins (83%)**.
- From **2026-07-05 to 2026-08-02 inclusive — twenty-nine consecutive days — the count is exactly
  zero**, every single day. (Verified across both the live log database and the archive database.)
- **Today, 23 Google logins and zero email logins**, seven of which created brand-new accounts. Total
  daily logins jumped from a July median of about 7 to 23.

**Root cause, precisely.** Commit `f5053be1` (2026-07-04 01:15 UTC), whose message is *"Apply 07-03
log-review fixes and expand admin analytics dashboard"*, added `script.crossOrigin = 'anonymous'` to
the shared third-party script loader at <File path="site/src/lib/auth/load-script-once.ts" />. That
attribute turns a script tag into a cross-origin request, which only succeeds if the origin answers
with a permissive `Access-Control-Allow-Origin` header. Google's `accounts.google.com/gsi/client`
sends no such header. The script therefore never loaded, the sign-in dialog rendered an orphaned "OR"
divider with no Google button, and nothing threw an error that reached telemetry.

**Why the lane recommended it.** The intent was sound: `crossorigin="anonymous"` is the standard way
to un-mask the browser's opaque `Script error.`, and this review sees a dozen of those a day. It is
correct on an origin that permits it (`kit.fontawesome.com` returns `access-control-allow-origin: *`).
It is destructive on an origin that does not. The recommendation was written as a blanket hardening
step rather than a per-origin one.

**Why it survived thirty days.** The report carried "Add `crossorigin="anonymous"` to external
scripts — still open, N opaque `Script error.` rows tonight" as an unstruck action item on eight
consecutive nights. Each night it was verified as *not yet applied to the remaining scripts* — never
as *does the thing it already applied still work*. The verification asked whether the change had been
made, not whether the feature still functioned.

**Status: fixed.** Commit `947c1ea8` (02:25 UTC today) made the attribute an opt-in `{ cors }` option,
default off, and removed a duplicate competing loader in `AuthModal.svelte`. The rule — *this
attribute is a per-origin decision, verified against that origin's real response headers, never a
blanket one* — is now standing law in this lane's decisions file and has already been written into
house's copy of the same file as a comment. **The remaining work is not the fix; it is making this
class of silent failure detectable.** See §6.

<Callout type="warn" title="The generalisable lesson, stated for the fleet">
When a review recommends changing how a <strong>third-party integration loads</strong>, the acceptance
test is that integration's own success metric — <em>are people still signing in with Google?</em> —
not the absence of new error rows. A broken integration usually produces <strong>fewer</strong> log
rows, not more.
</Callout>

The picture is unmistakable: before the deploy the day is flat green with two spikes; after it, the
floor never returns.

**Most likely mechanism, from reading the code — but not yet proven, and it must be instrumented
before it is changed.** The five-minute sweep at
<File path="site/src/lib/db/server/audio-derivative-sweep.ts" /> runs synchronously inside the serving
process and does two expensive things per run:

1. A `LEFT JOIN` over the 155,000-row media ledger whose join key is a computed string
   (`substr(original.key, 1, instr(original.key, '/audio/') + 42) || '_p1.mp3'`). A computed
   expression cannot use an index, so this is a full scan of the table, every five minutes.
2. For up to 160 candidate rows it opens **a separate dictionary database file each**
   (`new Database(dictionary_db_path(row.dict_id), …)`) and queries it — up to 160 synchronous file
   opens per sweep, on the thread that answers requests.

The conversion itself is well-behaved: `ffmpeg` is spawned as a child process at `nice -n 19` with a
concurrency cap of 2, so it competes for CPU but cannot block the event loop. The *scan* can.

**User impact so far: latency, not errors.** No user-observed HTTP 5xx outside deploy windows. The
synthetic uptime probe's worst response went from 1,247 ms (before) to **8,474 ms** (after) while its
median was unchanged — the same "the tail is what hurts" signature.

**Recommended order of work:** instrument first (§5.1), then fix the scan. This mirrors the standing
rule that cost this lane a wrong attribution before.

### 1.3 🟠 P2 — last night's unexplained freeze has a name: the catalog reconcile, once per deploy

Last night this lane inferred from timestamps alone that the half-hourly share-snapshot builder froze
the server. Instrumentation shipped this morning, and the inference was right — but the shape is more
specific and more fixable than expected.

Twenty-one sweeps ran today. **Eighteen of them blocked the event loop for 19–130 milliseconds.**
Three blocked it for **9,309 ms, 11,593 ms and 7,074 ms** — and in all three the entire cost is a
single step called `reconcile`:

```
02:33:20  blocking_ms 9,309   step_ms.reconcile 9,263    ← first sweep after the 02:30 deploy
05:03:22  blocking_ms 11,593  step_ms.reconcile 11,544   ← first sweep after the 04:47 deploy
14:03:16  blocking_ms 7,074   step_ms.reconcile 7,073    ← first sweep after the 13:57 deploy
```

The reason is one line of code: `reconcile_once_per_process()` in
<File path="site/src/lib/db/server/r2-snapshot-builder.ts" line="97" /> guards itself with a
module-level boolean, so the full dictionary-catalog reconciliation — which walks every one of the
~1,284 dictionary databases synchronously — runs on the **first sweep after every container boot**,
and never again in that container's life.

**So each deploy buys exactly one 7–12 second freeze**, arriving 3–16 minutes after the container
starts. It is not random and it is not the sweep; it is a boot-time job hiding inside a periodic one.

**Recommended fix:** move the reconcile out of the request-serving process's first sweep — either
into the same niced child process that already runs the nightly maintenance, or chunk it with a yield
between dictionaries the way the analytics compute was chunked. Either way, `blocking_ms` already
exists to prove it worked.

The freeze lands **before** the new container starts (`server_started` is logged at 02:29:51, 04:46:59
and 13:56:28), so this is the *currently serving* container being starved while the box builds the
next image. A load average of 2.12 on a two-core machine means both cores were saturated.

The build is invoked as a bare `docker compose build` at line 169 of `/opt/hosting/sveltekit/deploy.sh`
with no CPU limit anywhere, and the compose file sets no CPU reservation for the serving containers.

(02:30:03 ×2, 04:47:28) — that part is the expected blue/green swap cost, but the 24-second freeze
before it is not.

<Callout type="info" title="Speakable framing for this decision">
Every time we deploy, the live site stops answering for up to twenty-four seconds while the server
builds the new version, because the build and the site share the same two processor cores with no
priority given to the site. The choice is whether to give the running site priority over the build.
Recommended: yes — it is a configuration change, not a code change.
</Callout>

Because the Docker daemon (not the shell) performs the build, prefixing the command with `nice` does
nothing. The two workable levers are (a) give the serving containers a higher CPU weight in the
compose file so the build's containers yield under contention, or (b) run builds through a dedicated
buildx builder container that is itself CPU-constrained. Worth Jacob's call on which.

### 1.6 🟠 P2 — a contributor tried four times over eighty minutes to add photos, and was told nothing she could act on

Vincent (a contributor on the Iipay Aa dictionary, account created 2022) attempted four photo uploads
between 15:36 and 16:52 UTC. All four were rejected with HTTP 415:

| Time | File size | Format | What the server said | **What she saw** |
|---|---|---|---|---|
| 15:36:32 | 2.5 MB | `image/heic` | "This HEIC photo could not be converted. Please convert it to JPEG…" | `Failed to upload file (status 415).` |
| 15:37:07 | 2.5 MB | `image/heic` | same | same |
| 15:39:58 | 0.7 MB | `image/heic` | same | same |
| 16:52:54 | 3.7 MB | `image/heic` | same | same |

She was on Chrome for Android, in the middle of editing entries (the breadcrumbs show her clicking
"Save" between attempts). The design intends the browser to convert HEIC to JPEG before upload, but
that conversion uses `createImageBitmap`, which only Safari can do for HEIC. Non-Safari browsers fall
through to the server's net — and the server cannot decode it either: the image library on the box
reports HEIF support whose only decodable file suffix is `.avif`, i.e. no HEVC-coded iPhone HEIC.

**So the 415 is arguably the correct answer. The bug is that the helpful sentence never reaches the
person.** The upload helper at <File path="site/src/lib/media/upload-media.ts" line="165" /> rejects
with `new Error(\`Failed to upload file (status ${xhr.status}).\`)` and discards the response body
entirely — which is why the same generic string appears in the telemetry.

This is the **first ever** HEIC 415 in the logs (checked across the live and archive databases), so it
is not a regression — it is a path nobody had walked until today. Two things are worth fixing: surface
the server's message, and record it in `media_upload_failed` so the next occurrence is legible.
