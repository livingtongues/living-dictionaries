### 1.1 🔴 Ninety-two minutes on a dictionary that could never load — the self-heal cannot reach old tabs

A visitor on an Android phone opened the **Jewish Neo-Aramaic** dictionary's word list at 16:49 UTC.
Every attempt to start the local database asked for the same file:

```
https://livingdictionaries.app/_app/immutable/workers/chunks/62yDn_gc.js
```

That path is content-hashed, which is exactly what makes this hopeless: a 404 there is permanent for
that copy of the app. Only loading the current build can help. The app tried anyway — **24 leader
start failures and 14 give-ups in the first session (16:49→18:03), then 28 more in a second session
(18:03→18:37)** — plus one failed initial sync, one "Internal Error" page, and a bundle read that
timed out with no leader to answer it. Ninety-two minutes of a spinner on a page that was never going
to work.

**Why the fix we already shipped did not fire.** The reload-once classifier lists this exact browser
phrasing first (<File path="site/src/lib/db/client/stale-build-artifact.ts" line="46" />), and it did
fire tonight for three other people — two iPhones and one more — producing clean `stale_bundle_reload`
rows that ended their ordeals in seconds. It could not fire here because **the phone was running a
build from 2026-07-24T12:22 UTC and the classifier shipped on July 31**. A recovery mechanism ships
*inside* the bundle; a tab older than the mechanism contains none of it. This is standing law here
(2026-07-31), and tonight is its clearest illustration yet.

**Tonight's residual population, enumerated server-side** (sessions with ≥10 storm rows):

|---|---|---|---|---|
| `cbf3e238…` | Android | **2026-07-24** | 38 | 16:49 → 18:03 |
| `78569839…` | Android | **2026-07-24** | 28 | 18:03 → 18:37 |
| `0f6a2b9b…` | macOS | 2026-07-30 | 31 | 00:06 → 20:48 |

| `2cbafc64…` | Windows/Firefox | current build | 25 | 13:36 → 18:40 |

Six sessions, three of them on bundles that predate the fix. None can heal itself.

**The only lever left is on the server, and there is a good one: stop deleting the previous build's
assets.** Today's deploy replaces the container, and with it every file under `_app/immutable/`. If a
deploy instead *merged* the new build's immutable directory over the previous one or two builds'
(they are content-hashed, so names never collide), a tab from last week would keep loading the chunk
it asks for and would simply keep working until its next natural reload. That is a server-side lever
an old client already obeys — no client change, no forced reload, no conflict with the July 9 ruling
against reloading forgotten background tabs. It costs disk (the client build is tens of megabytes; the
volume is at 24% of 96 GB).

*Nothing here changes the triage rules: individual stale tabs are known-noise and I have not
re-triaged them. What is new is the size of one visitor's loss and a concrete server-side remedy.*

### 1.2 🟠 A contributor's edits were dropped six times — a null field kills the save

Three times between 03:51 and 04:25 UTC, on three different Kayan Baram entries, one contributor's
browser threw:

```
TypeError: Cannot read properties of null (reading 'trim')
```

The breadcrumbs are painful to read — the first instance is six "Save" clicks over seven minutes on
one entry, the second is a recording session (`Tap to Record` → `11s Stop Recording` → upload →
`Save` → `Save`). The save function throws *before* it calls the update and *before* it closes the
dialog, so from her side nothing happened and the obvious response is to click Save again.

**The path, read from source, is a chain of three defaults that all miss `null`:**

```
EntryDisplay.svelte   value={fields?.phonetic}        ← SQLite NULL for an empty field
  → EntryField.svelte     value: string               ← typed non-null; TypeScript is not strict here
    → EditFieldModal.svelte  value = ''               ← a default only fills `undefined`, never `null`
      → EditField.svelte     value = $bindable('')    ← same
        → save():            await on_update(value.trim())
```

<File path="site/src/lib/components/entry/EditField.svelte" line="39" />. A default parameter in
JavaScript applies to `undefined` only, so a database `null` sails through all three and arrives at
`.trim()`.

**Recommended fix (one pass, both halves):** normalise at the boundary — `value ?? ''` where
`EntryField` hands the value down — *and* make `save()` itself null-proof, *and* include the `field`
name in the error context. The last part matters because the line above `.trim()` already tries to
guard (`inputEl?.value || value || ''`), so something about the binding read-back is not yet
explained; knowing which field it was will settle it in one day rather than by argument.

**The cause is visible in the source.** The render worker fetches a font subset from Google Fonts for
any glyph the bundled font cannot draw, and memoises the result — but the memo key is the script code
joined with **the entire text being drawn**:

```js
// site/src/routes/og/render-worker.js
const key = args.join('|')          // → "unknown|cʰiletumõkʰoʔɽeʔ"
```

Every headword is unique, so **every card is a cache miss**, and every miss costs up to two sequential
network round-trips (the stylesheet, then the font file) each bounded at 3 s — repeated per text run
on the card. Three runs is nine seconds against a ten-second deadline.

The evidence agrees: the failures repeat on the same handful of dictionaries, all of which use
letters outside the base font — **GtaɁ (10 today), Sora (5), Boie'nen (5), Sengwer (3), Ɨshɨr,
Matukar, Garifuna, Werikyana**.

**Recommended fix:** key the cache by *family plus the sorted set of characters that actually needed
the fallback*, not the whole string. Every GtaɁ headword shares the same handful of rare glyphs, so a
whole dictionary collapses into one cached subset and the tail disappears. Persisting the subsets to
disk beside the card store would also survive worker restarts.

### 1.4 🟠 Burmese share cards get no font at all — and the "unmapped" alarm cannot fire

One card today asked for Burmese text (`ငါဟ်းငုတ်တယ်`) and produced two warnings in a row:

```
font_fetch_status  status 400  family Noto+Sans  script "unknown"
font_unavailable                families Noto+Sans  script "unknown"
```

satori did not recognise Myanmar script, so it passed script code `unknown`. In
<File path="site/src/routes/og/font-map.ts" line="73" /> `unknown` is mapped to plain Noto Sans and is
therefore reported as **`mapped: true`** — the "nothing is mapped for this script, its glyphs will be
missing" warning cannot fire for it by construction. Google Fonts then answered **400** (it will not
subset a font for characters it does not contain), and the visitor got the generic card.

**Recommended fix:** when satori says `unknown`, look at the text ourselves — a Unicode-block check is
a few lines — and add the obvious missing families (Myanmar first; Khmer, Lao, Sinhala, Ethiopic,
Armenian, Georgian and Cherokee are the same class of gap). Per standing law, close this by
**rendering an affected card and looking at it**, never by the absence of new error rows.

## 5. Coverage gaps (Phase B)

Prioritised by "would this have answered a question I could not answer tonight?"

1. **`og_render_worker_timeout` cannot name the card that timed out.**
   <File path="site/src/routes/og/render-pool.ts" line="219" /> emits only `{ render_timeout_ms, width,
   height }`. Its sibling failure event carries `{ dict, title }`; the timeout does not, so 46 rows a
   day say only "something took too long". Add the job's dictionary and title — and the worker's
   `last_dynamic_asset` (script + family), which is already tracked in the worker and would have made

2. **Nothing measures the font-subset cache.** A hit/miss counter (or an
   `og_font_subset_fetched { family, chars, ms, cached }` warning above ~1 s) is the numerator *and*
   denominator this subsystem lacks — the standing "never compute health from failures alone" rule.

   <File path="site/src/lib/utils/load-once.ts" /> (used for Mapbox and Keyman) rejects with the raw
   `Event` and has no `crossorigin` option; <File path="site/src/lib/auth/load-script-once.ts" /> fixed
   both. **I checked both origins' real headers tonight**, as the standing per-origin rule requires:
   `api.mapbox.com` → `access-control-allow-origin: *`; `s.keyman.com` → `access-control-allow-origin: *`;
   `accounts.google.com/gsi/client` → **no such header** (leave it off, forever). Porting the option and
   enabling it for those two origins should give a message and a stack to the 34 opaque `Script error.`
   rows a day.
4. **Dropped telemetry inserts are invisible.**
   <File path="site/src/lib/server/insert-client-log.ts" line="125" /> swallows a failed insert into a
   console line that dies with the container, while the endpoint still answers "ok". Count them and
   report the count on the host-stats sample. *(Borrowed from house's finding tonight.)*
5. **No robot filter at ingest.** 62 service-worker `Rejected` errors a day come from crawlers and are
   stored in full. house filters informational crawler events at ingest; this family is a warning, so
   even their filter would need widening. *(Borrowed from house.)*
6. **Chat polling should catch its own fetch failure** (§1.9) — a handled `chat_poll_failed` warning
   with `{ online, consecutive_failures }` instead of an unhandled rejection.
7. **Carried, unchanged:** log the 409 sync refusal server-side (`dict_changes_refused`); emit a
