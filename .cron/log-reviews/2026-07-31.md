### 1.1 🔴 A tab that never reloads can never receive the fix written to save it

This is the finding of the night, and it generalises past this app.

Every self-healing mechanism the dictionary client has — the reload-once rule for deleted build
files (shipped this morning), the schema-outdated auto-reload (shipped 2026-07-12), the OPFS file
replacement — lives **inside the JavaScript bundle**. A browser tab that has been open, untouched,
since before that code shipped is running the *old* bundle, which contains none of it. It will never
heal, because healing is a feature of a version it does not have. And the only way to get the new
version is the exact action it cannot take on its own: a reload.

Two real signed-in people are underneath that floor right now.

**Evelyn Halstead — failing continuously since at least 2026-07-17, on the `solari` dictionary.**
One single browser session (`49ad2afc…`) has now written **1,266 failed-sync rows**, 479 of them in
this window alone (15:47 → 20:55 UTC, roughly one every 40 seconds). Her tab is running the bundle
built **2026-07-05 09:52 UTC**. The server answers each attempt with HTTP 409 `schema_outdated` —
correctly, because her local database is 26 days behind the current schema. The code that turns that
409 into an automatic reload landed on **2026-07-12** (commit `a5c30731`), a week *after* her bundle
was built. Her session has therefore never logged a `schema_outdated_reload`, never logged the
`schema_outdated_reload_gave_up` fallback, and never shown her the "app update needed" prompt. She
has no idea; from her side the dictionary simply stopped saving. The oldest row in the whole logs
database is 2026-07-17, so 14 days is a *floor*, not a measurement — this may have been going on far
longer.

**Rebekah Ingram — locked out of her own private `algonquin` dictionary for a third day.** Same
session id as in last night's report (`d22601c2…`), still on the bundle built **2026-07-29 13:04
UTC**, still failing on the same deleted worker file
(`/_app/immutable/workers/chunks/DASUsDk6.js`). She wrote 30 more boot-failure rows across this
window, in three clusters (07-30 22:29, 07-31 07:14–07:16, 07-31 14:29) — she is coming back to the
tab and trying again. The reload-once rule that would fix her in one second shipped at 07:01 UTC
today, into a bundle her tab will never fetch.

**The rule itself is fine and is working** — for tabs that are on a build that has it. Two
`stale_bundle_reload` rows fired today, both classified `missing_build_artifact`, one anonymous
(`taiwanese-hokkien-tai-gi`, 08:39) and one signed-in (`conlangjupus`, 19:50), and neither session
produced any further boot failure. That is the mechanism working exactly as designed.

<Callout type="warn" title="The general rule this establishes">
A client-side self-heal can only ever reach the population that has already reloaded since it
shipped — which structurally excludes the long-lived stuck tabs that are its whole reason for
existing. Any future recovery mechanism needs either a server-side lever that an OLD client already
understands, or an accepted human-nudge path. Assume the residual population is never zero, and keep
it enumerable: tonight it is exactly **two sessions**.
</Callout>

**Action:** nudge both people by email (a hard refresh, Ctrl/Cmd-Shift-R, fixes both instantly), then

list is cheap to regenerate: sessions with ≥10 sync/boot failures whose `app_version` predates the
relevant fix. Tonight that query returns four sessions, of which two are genuinely stuck and two are
ordinary transient network failures.

**HTTP 200** when I fetch them now, so these are intermittent, not a broken route.

Two mechanisms could explain the silence and the logs cannot separate them:

1. `handleError` runs but its write is lost — the insert is wrapped in a `try`/`catch` that swallows
   everything, and `log_server_event` swallows again on top of it, so a failure at either layer
   leaves no trace anywhere.
2. `handleError` never runs, because the failure happens during *client-side* navigation rather than
   server rendering. There is **no `hooks.client.ts` in this repo at all**, so a browser-side load
   failure produces SvelteKit's default "Internal Error" page with nobody logging the cause.

Both are worth closing, and closing them is cheap: give `handleError` a short random `error_id`,
put it in both the server row and the message the browser shows, and add the missing
`hooks.client.ts`. A client row that carries an `error_id` proves the server saw it; one that does
not proves the failure was client-side. Filed with the full reasoning in
<File path=".issues/ssr-500-has-no-server-side-record.md" />.

### 1.4 🟡 A plain `?q=word` search link is silently thrown away

77 `malformed_query_param` warnings, all for the key `q`, from 3 sessions. The raw values are
perfectly ordinary searches: `birthday`, `santa`, `sant`, `san`.

The entries view registers `q` as a **JSON object** (`{"page":1,"query":"birthday"}` — see
`routes/[dictionaryId]/entries/+page.ts`). When the value in the URL is a plain string instead, the
parser cannot read it, logs this warning, and **replaces the whole thing with an empty object**. So
`https://livingdictionaries.app/garifuna/entries?q=birthday` — the URL a person would guess, an LLM
would construct, or a search engine might index — opens the unfiltered entry list with an empty
search box. The searcher's intent vanishes with no error shown.

The second half is a leak. The warnings for `?q=santa` came from **`/admin/dictionaries`**, a page
that has nothing to do with the entries view and stores its own `q` as a plain string. Each
`QueryParamState` creates a permanent `$effect.root` subscription to the page URL and exposes a
`destroy()` method — which **no application code ever calls** (only the test file does). The instance
built by a visit to `/{dict}/entries` therefore stays subscribed for the rest of the tab's life and
keeps reacting to every unrelated URL, including one keystroke at a time as an admin types in an
unrelated search box. Harmless today (it warns but does not overwrite), untidy and unbounded in
principle. Both halves filed in <File path=".issues/entries-q-param-and-leaked-query-param-state.md" />.

### 1.5 🟡 "Script error." — 23 opaque rows during a real editing session

Two users, 21 of the rows from one: a contributor editing the `ndau` dictionary between 02:22 and
04:49 UTC (2.5 hours, 13 entries opened, 7 media uploads, 2 entries deleted, 1 created — a
productive session). Her breadcrumbs show clicking Save, then Back, then a run of rapid clicks, then
these errors, repeatedly (one row carries `repeat_count: 16`).

`Script error.` with `filename: ""`, `lineno: 0` is the browser's deliberate blackout for an
exception thrown by a script loaded cross-origin **without** a `crossorigin` attribute — the browser
refuses to reveal anything. We cannot tell whether this is a third-party script or our own asset
served from another origin. It cost this contributor nothing visible (her work saved; no sync errors
in her session), which is why it sits at 🟡 — but 23 completely opaque errors inside a real editing
session is a coverage hole, and the fix is one attribute. See §5.
