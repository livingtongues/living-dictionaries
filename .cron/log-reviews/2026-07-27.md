**Every non-deploy outage minute — 17:35, 18:44–18:45, 19:00–19:04, 19:50, 20:19–20:21 — falls inside
a minute that also produced share-image render failures.** Five out of five. The share-image endpoint
runs on a roughly five-minute crawler cycle, and the outages ride that cycle.

**Why the share-image endpoint can do this** (measured tonight inside the production container with a
read-only probe):

- one cold card render costs **~700–840 ms** of the single Node thread;
- **8 concurrent renders** stretched to **5.0–5.7 s each**, and while they ran, the trivial
  `/healthz` endpoint — which returns the string "ok" and touches nothing — took up to **3,251 ms**.
  Caddy's health timeout is **2 s**. That is the production failure, reproduced on demand.
- the photo transcode is *not* the cost: `sharp` converts a WebP to JPEG in 56–88 ms and does eight
  of them concurrently in 290 ms. The expense is `satori` + `resvg`, both synchronous, now
  rasterizing a ~193 KB embedded photo per card.

**Why now:** between July 23 and this morning, every photo card threw `Unsupported image type:
image/webp` almost immediately and fell back to a cheap text-only render. That failure was
accidentally acting as a rate limiter. This morning's (correct) fix restored the photo and with it
the full render cost.

**Three unbounded things in that endpoint**, all in
<File path="site/src/routes/og/component-to-png.ts" />:

1. **Memory** — the render cache is a plain `Map` with no size limit holding every ~220 KB PNG for
   the life of the process. Live proof: the serving container sits at **2.87 GiB** of memory after
   7 hours, versus **1.17 GiB** for the standby that booted at the same moment and ran the same
   background jobs but takes no traffic. That ~1.7 GiB gap implies roughly **1,000 card renders per
   hour**.
2. **Concurrency** — nothing limits simultaneous renders, so a crawler burst maps one-to-one onto
   simultaneous CPU-bound work.
3. **Outbound network** — the Google Fonts fetch has **no timeout**, once per unique text run.
   Production logs show repeated `Failed to load dynamic font … ETIMEDOUT`, and in those same windows
   the R2 photo fetch (13–150 ms when the box is idle) fails outright — the 84
   `og_image_transcode_failed` rows. Even the hourly R2 snapshot uploader hit `ETIMEDOUT` once.

**The fix is not to undo this morning's work.** It is to render each card once and store it, cap
concurrency, cap the cache, and time-box the font fetch. Full detail, evidence and proposed order in
<File path=".issues/og-endpoint-load-outages.md" />.

Jacob's standing rule from this morning — *analytics and telemetry must never block a request path* —
generalises: the question is never "is it fast enough", it is **"whose request pays for it."** For a
share card the answer should be "nobody's — it was rendered once and stored."

### 1b. 🟠 Share cards render tofu for non-Latin scripts (unmasked, not new)

`og_render_failed` with `reason: "font"` went from ~3/day to **127/day**. This is not a new fault —
it is an old one that finally gets reported. The underlying error is the long-standing font-parser
limitation `lookupType: 5 - substFormat: 3 is not yet supported`, thrown while parsing a Google font
fetched on the fly for a non-Latin script. Until today the WebP image error threw first, so this one
never surfaced.

It is a warning on a retry path: the card still renders, using only the bundled Noto Sans. The
visible cost is that scripts without a bundled fallback come out as empty boxes. Verified by eye on a
live card: the Manchu dictionary's card shows `□□□□` where the Manchu gloss should be, while the
Chinese gloss on the same card renders correctly.

Low priority and cosmetic. The durable fix is to bundle more static Noto script fonts (or skip the
dynamic-font path for the scripts known to trip the parser) rather than to keep fetching fonts at
render time — which also removes one of the unbounded outbound-fetch sources in §1a.

## 5. Coverage gaps (Phase B)

Tonight's investigation needed four things the logs did not have. Each is small.

**5.1 — The share-image endpoint logs only its failures.** `/og` emits `og_render_failed` and
`og_image_transcode_failed` and nothing else, so its request volume, its cache hit rate and its
duration are all invisible. **Tonight I had to infer its traffic from the container's memory growth**
— roughly a thousand renders an hour, deduced from a 1.7 GiB gap between the serving and standby
containers. That is not a sustainable way to measure a top-of-list workload.
*Path:* `site/src/routes/og/+server.ts` → *event:* `og_rendered` → *level:* `info` → *fields:*
`{ duration_ms, cache: 'hit' | 'miss', transcoded: boolean, has_photo: boolean, dictionary_id }`.
*Why:* would have identified the outage cause in one query instead of six. **Highest value item here.**

**5.2 — No slow-request telemetry anywhere on the server.** `hooks.server.ts` logs errors and 404s
only; a request that succeeds after eight seconds leaves no trace. Every "the site felt slow" question
currently requires reproducing it by hand.
*Path:* `hooks.server.ts` `handle` → *event:* `slow_request` → *level:* `warn` → *fields:*
`{ route_id, path, status, duration_ms }`, emitted only above a threshold (1 s) so volume stays tiny.
*Why:* this is the single instrument that turns "something was slow" into "this route was slow".

**5.3 — `host_stats` measures the machine but not the process.** The five-minute sample carries CPU,
memory, swap and disk for the whole host, but nothing about the Node process itself. Adding
`rss_mb`, `heap_used_mb` and an **event-loop lag** measurement (max/p99 observed over the same
five-minute window) to the existing event costs zero extra rows and would have made both tonight's
findings — the memory climb and the multi-second stalls — visible on a chart instead of requiring a
`docker stats` session.
*Path:* `site/src/lib/server/host-stats.ts` → *extend the existing* `host_stats` *event*.
*Why:* it is the cheapest possible early warning for exactly this failure class, and it is the
server-side twin of tutor's client `js_thread_stall` watchdog (§6).

**5.4 — Third-party script errors arrive blank.** The `Script error.` cluster (§1e) is 92 rows a day
of pure void: no message, no file, no line. The one-line unmasking step is `crossorigin="anonymous"`
on the third-party script tags that support it (Google sign-in does; Keyman's CDN needs checking).
*Why:* low priority — but it is currently 40% of the day's raw error rows and we cannot say whether
any of it is ours.

Deliberately **not** proposed: any additional per-user sync telemetry (already rich), and any new
event on the entry-edit path (already well covered by `entry_created` and the change-push events).

## 6. Dashboard improvements (Phase C + D)

### Phase C — the dashboards said everything was fine while the site was down

This is a grounded proposal, not a backlog re-run.

The `/admin/health` **Synthetic uptime** panel reports availability from a probe that runs every five
minutes from an outside machine. Today it recorded **271 probes and 2 failures — 99.3% availability**.
Meanwhile Caddy refused **1,553 real requests** and 21 signed-in users hit HTTP 502. A five-minute
probe cadence against one-to-three-minute outages will miss them roughly four times out of five, and
today it did.

**Proposal — "user-observed availability" alongside synthetic uptime.** The signal already exists and
nothing reads it as availability: `sync_failed` rows carry an HTTP `status`, and 502/503 responses
there are, by definition, real users getting no server. Fold them into the existing uptime panel as a
second series:

- **daily count of user-observed 5xx responses**, and the **distinct users affected** (today: 152 and
  21) — a stability number, not an error list;
- the **worst hour** of the day, so a burst pattern is legible at a glance;
- keep the synthetic series next to it: the gap between "our probe says up" and "users say down" is
  itself the insight.

This obeys the standing shape rules — aggregate subsystem health, no scrollable per-error feed
(2026-07-14), interpretation over inventory (2026-07-22) — and needs no new telemetry. Filed to
<File path=".issues/future/dashboard-improvements.md" />.

**Load-performance watch:** `/admin/analytics` and `/admin/health` were **not opened by anyone today**
— zero `admin_analytics_computed` rows — so this morning's caching work still has no production
timing evidence. It cannot be declared verified yet. One thing to keep an eye on: the warm-up now runs
from the retention cron, which fired at 20:17 on **both** containers simultaneously (they booted
together at 14:17), and the 20:19–20:21 outage sits right after it. The share-image burst is the
better-supported explanation for that window — but a background job that runs on the primary and the
standby at the same instant deserves a jittered schedule regardless.

unbounded properties. Also worth broadcasting: **a five-minute synthetic uptime probe cannot see a
one-minute outage** — all three apps' uptime panels share that blind spot, and all three already log
the user-observed 5xx signal that fixes it.

## Recommendations / action items

- [ ] **Stop the share-image endpoint from taking the site down.** Render each Open Graph card once,
      store it outside the process, and cap how many can render at the same time.
      <File path=".issues/og-endpoint-load-outages.md" /> has the measurements and the proposed order.
      **This is the only item today with evidence of total, site-wide user impact** — 1,553 refused
      requests and 21 signed-in users failing to sync, five times this evening. In plain terms: the
      site is currently taken offline for a minute or two, several times an evening, by a robot
      asking for preview pictures.

- [ ] **Add success telemetry to the share-image endpoint** (§5.1) before or alongside that fix —
      one `info` event per render with its duration and whether it was cached. Tonight its traffic had
      to be inferred from container memory growth, which is not repeatable.

- [ ] **Add process memory and event-loop-stall measurements to the existing five-minute host sample**
      (§5.3). Zero extra log volume, and it is the cheapest early warning for this entire class of
      failure. The serving container is currently at 2.87 GiB and climbing between deploys with
      nothing watching it.

- [ ] **Add slow-request logging above a one-second threshold** (§5.2). Today a request that succeeds
      slowly leaves no trace at all, so "the site felt slow" is unanswerable without a live
      reproduction.

- [ ] **Build the user-observed availability series into the health dashboard** (§6). The uptime panel
      claimed 99.3% on a day with five total outages; the corrective data is already in the logs.

- [ ] **Bound the give-up path for the dictionary self-heal** (§1c) so one stuck device cannot emit 38
      identical reports in a single session, as one iPhone did on tuscarora tonight. The underlying
      iOS case stays open in <File path=".issues/dict-boot-persistent-opfs-recovery.md" />.

- [ ] **Watch:** anonymous visitors occasionally waiting 20 seconds to 15 minutes for a dictionary that
      never finishes opening (§1d, `had_leader: false`). Eleven sessions today, all anonymous, all
      self-healing. Escalate if a signed-in editor is affected.

## Needs a decision

- **Share-card text for non-Latin scripts** (§1b). Dictionaries in scripts we do not bundle a font
  for — Manchu is the confirmed example — currently render empty boxes in their social preview image
  instead of their own writing. Fixing it means shipping several more script fonts with the app,
  which makes the download bigger for everyone, or accepting the boxes for those languages.
  *Recommended default:* bundle the handful of scripts that actually appear in Living Dictionaries
  content rather than all of them, and do it as part of the share-image rework above, since removing
  the render-time font fetch also removes one of the causes of the outages. It is cosmetic, so it
  should not delay the outage fix.
