### 1a. 🔴 The share-card store is 1,000 cards wide and the card space is unbounded

Yesterday's *correctness* fix worked — this is a *capacity* fault sitting underneath it, and it has
been there since the disk store shipped on 07-28.

`site/src/routes/og/card-store.ts` caps the store at `MAX_ENTRIES = 1000` (and `MAX_BYTES =
250_000_000`). Cards average **173 KB**, so the *entry* cap binds first, at 70% of the byte budget.
The store on the box right now: **1,015 files · 176.1 MB · newest file 30 seconds old**. It is
permanently full and permanently evicting.

Every `/og` URL is a distinct card — one per dictionary home *and one per entry* — and crawlers walk
all of them. So the store never converges; it churns:

**Why it matters beyond CPU:** a shed request is answered with the generic Living Dictionaries card
under a 60-second cache header, so the scraper comes straight back — and more than half the time
gets shed again. Roughly **one in two share links posted to Facebook, WhatsApp or Slack today showed
the generic card instead of the dictionary's own**.

**The fix is a budget, not an architecture change.** Raise the store to something proportionate to
the box: at 173 KB/card, **20,000 cards ≈ 3.5 GB** — 4.6% of the 75 GB free on `/data`. Ten of
thousands of the most-crawled cards would then be permanent file reads, the render queue would drain,
and the shed rate should collapse. Recommended as the top action item; the byte cap stays the real
guard rail.

### 1b. 🟠 One wedged tab produced three-quarters of the day's errors

An anonymous visitor on **Windows / Chrome 150** opened `/bahasa-lani` at **16:25:58 UTC**. The
session reports `has_opfs: true`, `db_tier: "opfs-worker"`, page load 788 ms — a perfectly capable
machine. 235 ms later the recovery path fired `dict_boot_file_replaced` (`boot_message:
"sqlite3_open_v2"`), and then **it never recovered**:

- `leader_boot_failed` × **839**, `dict_boot_recovery_exhausted` × **421**, still firing at 21:24 UTC
  — five hours later.
- Every other session on `bahasa-lani` today opened it normally (`dictionary_opened` → `entry_opened`,
  no boot faults), and the server snapshot is a healthy 1.35 MB. **The fault is device-local OPFS
  state, not the dictionary.**

Two separate problems, both actionable:

1. **The give-up path is unbounded.** `dict-session.ts:91` logs on *every* `on_boot_failed` callback
   with no per-session cap, so one tab can dominate the error corpus — which is exactly what happened:
   421 of 569 client error rows (**74%**), pushing the forever `real_errors` metric from 117 to **312**.
   This is the identical "bound the give-up path" item recorded on 2026-07-27 (then: one iPhone on
   `tuscarora`, 38 rows). It is now four weeks' worth of evidence in one night, on desktop Chrome.
2. **The user is told nothing.** The only boot UI is the progress bar (`DictBootProgress`); nothing
   consumes `recovery_exhausted`. After a couple of exhausted attempts the visitor should get a plain
   message — *"this browser couldn't open the dictionary's local database; try reloading, or closing
   other tabs of this site"* — rather than a bar that spins for five hours.

## 5. Coverage gaps (Phase B)

Prioritized by "would this have answered a question I could not answer tonight?"

1. **★★★ `/og` store hits are invisible — the endpoint's denominator is unknowable.**
   `routes/og/+server.ts:113` returns a stored card with **no telemetry at all**, so tonight's "55%
   shed" is a share of the *known* requests only. Emit a coalesced counter (the 60 s
   `og-telemetry.ts` bucket already exists) — `og_card_served` with `{ source: 'store', ua_class }` —
   and one periodic `og_store_state` with `{ entries, bytes, evicted_since_last }`. Without the first
   we cannot compute a hit rate; without the second the eviction thrash in §1a stays invisible.
   *This is also a correction to a filed backlog item — see §6.*
2. **★★★ No requester identity on `/og`.** Nothing records the user agent or referer of a card
   request, so "is this Googlebot indexing, or people sharing links?" is unanswerable — and it is
   the question that decides whether to spend 3.5 GB of disk on §1a or to throttle crawlers instead.
   Add `ua_class` (`bot` / `social` / `other`, via the canonical `bot-user-agent.ts`) to the shed and
   render buckets. Cheap: it is a bucket key, not a new row.
3. **★★ The server never logs its own boot.** There is no `server_started` event anywhere in
   `hooks.server.ts` or `$lib/server/`, so correlating a 5xx burst with a deploy means reverse-guessing
   from client `app_version` first-seen timestamps — which is how I spent part of tonight. Emit one
   info row at boot: `{ app_version, commit, container: 'blue'|'green', is_standby, node_version }`.
   It also unblocks the long-parked "deploy-settling error band" backlog item, which needs deploy
   timestamps it does not currently have.
4. **★★ `dict_boot_recovery_exhausted` needs a per-session cap.** Covered in §1b — this is a coverage
   item as much as a bug: one client should never be able to author 74% of a day's errors. Cap at
   ~3 rows per session plus one final `…_gave_up` summary carrying the attempt count.
5. **★ `Failed to read dict bundle from wa-sqlite` is logged twice.**
   `src/lib/search/entries-ui-store.ts:126-127` calls `console.error(...)` (which the remote-log patch
   uploads) and then `log_event({...})` on the very next line. Every occurrence becomes two rows — one
   rich, one useless (`{"extras":["{\"code\":\"timeout\"}"]}`) with a *different* message (trailing
   colon), so it also splits into two clusters. Delete the `console.error`. It is the **only** such
   double-log in the codebase — I checked every `log_event` call site.
6. **★ No success-side sync event on the client.** `build_sync_health` reads only `sync_failed`. This
   is already the filed "sync liveness" backlog item and house independently proved its worth tonight
   (see §6) — noting it here only because it is genuinely a *coverage* gap, not a panel gap.
