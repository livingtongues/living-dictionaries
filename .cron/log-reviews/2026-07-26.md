### 1a. 🟠 Share images lost their photo on July 23 (new regression)

Every failure carries the same stack:

```
Error: Can't load image https://media.livingdictionaries.app/tutelo-saponi/photo/
  f648f1ee-…_w1600.webp: Unsupported image type: image/webp
    at satori@0.0.44/dist/index.js
```

The chain is short and certain:

1. `SeoMetaTags.svelte` builds the share-card photo URL with `photo_src({ photo, variant: 'w1600' })`.
2. Since commit `e4a9dfb4` (July 23, 10:38 UTC) that variant is **WebP** — `photo-variants.ts`
   writes `_thumb/_w900/_w1600.webp`.
3. `satori` 0.0.44, which renders the card, supports JPEG/PNG/GIF/SVG only. It throws
   `Unsupported image type: image/webp`.
4. `/og/+server.ts` catches it, logs `og_render_failed`, and re-renders **without the photo** — so
   scrapers get a valid but photo-less card rather than an error.

The daily count is a clean step change on the migration date:

### 1b. 🟠 Phantom unsaved work: 5,437 stale flags across 33 dictionaries

Two clients warned today that local edits were not draining (`dirty_rows_stuck`): a signed-in user on
**mahasuvi** (116 rows, unchanged since July 22) and an anonymous tab on **boienen** (2 rows, warning
since July 20). Both show `last_error: null` with `last_sync_at` advancing — the sync loop is alive
and healthy; the rows simply never clear.

This is **not new lost work.** It is exactly the root cause diagnosed on July 21 in
<File path=".issues/yokoim-dirty-rows-stuck-2026-07-20.md" />: rows that are already canonical on the
**server** still carry `dirty = 1`, the snapshot ships them to every client, and a visitor with no
editor role can never push (and therefore never clear) them. The open hardening checkbox in that
issue — normalize the flag server-side — is still unticked.

Tonight I measured the fleet-wide blast radius directly against the production dictionary databases:

| Dictionary | Stale flags | Table |
|---|---:|---|
| batsi-kop-tsotsil-tsot | 2,146 | `entry_dialects` |
| wancho | 1,163 | `entry_dialects` |
| south-saami | 1,078 | `entry_dialects` |
| galo | 499 | `entry_dialects` |
| sugtstun | 200 | `entry_tags` |
| mahasuvi | 116 | `entry_dialects` |
| udekau | 65 | `entry_tags` |
| algonquin | 39 | `entry_tags` |
| *…25 more dictionaries* | 131 | both |
| **Total** | **5,437 rows / 33 dictionaries** | only the two junction tables |

Every affected flag is in `entry_dialects` or `entry_tags` — never in a content table — which is
consistent with the July 21 finding that the flags were inherited from a bulk write, not from real
unsaved edits. Two consequences:

1. **Nobody's work is actually at risk**, but affected visitors' browsers push nothing and warn
   forever, and the tab believes it holds unsaved changes.
2. **The early-warning signal is poisoned.** `dirty_rows_stuck` exists to catch a genuine editor
   wedge; with 33 dictionaries emitting false positives, a real one is hard to see.

I verified the four (user, dictionary) pairs that warned this week — mahasuvi, batsi-kop ×2, yokoim —
and **none of those users holds a role on that dictionary**, confirming the pull-only inheritance
path rather than a broken editor.

### 1c. 🟡 Audio playback failing for a few visitors — rising, cause not yet visible

Four separate public visitors, on four dictionaries in four countries, tapped play and got a rejected
playback promise:

|---|---|---|---:|

The breadcrumb trail is unambiguous: `dictionary_opened → search_performed → click <entry> →
audio_played ×3` and then the failure, repeated — the visitor tapped again and again because nothing
played. The daily count is climbing: 1 → 1 → 3 → 8 → **19**.

I checked the obvious causes and ruled them out: I resolved the exact audio rows for the two
identifiable entries and **HEAD-requested 32 random audio files across all four dictionaries — every
one returned HTTP 200 with a correct content type** (`audio/mpeg`, `audio/wav`, `audio/x-m4a`).
The files are fine.

What remains is client-side, and **our telemetry cannot currently tell us which**: `Audio.svelte`
calls `audio.play()` with no `.catch()`, so the browser's generic rejection surfaces as a bare
`unhandled_rejection` carrying **no URL, no error name, no readyState, and no network state**. Per the
precedent set for the waveform decode error (2026-07-14 ruling: *enrich first, then diagnose, never
guess*), the first step is a proper `audio_play_failed` event — see §5.

## 5. Coverage gaps (Phase B)

1. **★★ `audio.play()` failures are invisible.** `routes/[dictionaryId]/entries/components/Audio.svelte`
   (module-level `playAudio`) calls `audio.play()` with no catch, so the rejection lands as a bare
   `unhandled_rejection` with no attribution. **Event:** `audio_play_failed` · **level:** `warn` ·
   **fields:** `{ dictionary_id, entry_id, audio_id, storage_path, error_name, media_error_code,
   ready_state, network_state, online }`. **Why:** this is the *only* reason §1c is a guess instead of
   a diagnosis, it is rising 1→19/day, and audio is a core reason communities use this site. Cheap:
   one `.catch()` on an existing call. *(Also worth showing the user something — right now a failed
   tap is completely silent, which is why they tap five times.)*
2. **★ `dirty_rows_stuck` cannot distinguish a real wedge from an inherited flag.**
   `report-dict-sync-failure.ts` sends only `{ dirty_rows, deletes, last_sync_at, last_error }`.
   **Add:** `{ tables: { entry_dialects: 116, … }, has_editor_role, oldest_dirty_updated_at }`.
   **Why:** tonight I could only tell these apart by querying 33 production databases by hand. With
   `has_editor_role: false` + `tables: {entry_dialects}` the row would self-classify as the known
   inherited-flag class, leaving the signal free to catch a genuine editor wedge. *(Its sibling
   fix — normalizing the flags server-side — removes the false positives at the source; the telemetry
   field keeps them distinguishable if they ever recur.)*
3. **★ Per-stage timings on `admin_analytics_computed`.** The event records `total_ms` only; the
   stage breakdown exists solely behind a developer environment variable. Recording the stage map
   inside the existing event turns "which query is slow?" into a lookup instead of a manual
   measurement session. *(Ported from house's July 26 review, which had to hand-measure the same
   thing.)*
4. ✅ **No new broad inventory item.** Import and media upload failure paths, entry writes, sync,
   snapshots, retention, email lifecycle, host resources, boot recovery, and the v1 API all emit
   durable structured events. Today's `og_render_failed` is a model case: the telemetry named the
   failure class precisely enough to diagnose a three-day-old regression from a single query.

Three facts make this a site-wide availability problem rather than an admin annoyance:

1. **It blocks everything.** The calculation is synchronous `better-sqlite3` work with no `await` in
   its path. For 27–80 seconds the Node process answers **no other request** — every reader, every
   contributor's sync, every crawler.
2. **Users felt it.** In the 18:17–18:22 UTC window on July 24, production logged **5 × `sync_failed`
   with HTTP 502** plus 8 `server_behind` retries — the reverse proxy giving up on a blocked backend.
   The same pattern repeats at 03:51:59 on July 25.
3. **It repeats needlessly.** `watermark-swr-cache.ts` single-flights *background refreshes* but a
   **cold miss computes inline**, so two simultaneous first visits each pay full price — visible as
   the identical same-second pairs above. And the cache is in-memory only, so **every deploy throws
   it away**; with several deploys a day, "cold" is the normal state.

**has already built the fix** — yield-between-stages, disk-persisted cache payloads, single-flight on
miss, and an index jump-scan replacing the distinct-user-agent scan (6,756 ms → 3 ms). LD's copy of
that scan is `log-analytics.ts:941`, over a **2 GB** file — bigger than house's. Full port plan:
<File path=".issues/analytics-compute-blocks-server.md" />.
