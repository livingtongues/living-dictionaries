## 5. Coverage gaps (Phase B)

These are recommendations only. Current source was checked before each one was retained.

1. **Dictionary boot terminal outcome — highest urgency.**
   `dict-session.ts` → `dict_boot_recovery_exhausted` → `error` once per page session, with
   `{ dict_id, boot_message, last_stage, attempt, repeat_count, visibility, was_hidden }`.
   This would have turned 421 indistinguishable rows into one actionable foreground wedge and makes
   a user-visible failed state measurable.

2. **Open Graph terminal outcome and store pressure.**
   `routes/og/+server.ts` → exactly one `og_card_served` → `info` for every request, with
   `{ source: 'disk'|'r2'|'render'|'generic', ua_class }`; add a bounded periodic store-pressure
   event with `{ entries, bytes, evictions }`. `degraded_response()` currently emits no terminal
   row, while one request can emit several failure rows, so the present numerator cannot be treated
   as a success rate.

3. **Per-dictionary R2 snapshot failures.**
   `r2-snapshot-builder.ts` → `r2_snapshot_failed` → `warn`/`error`, with
   `{ dictionary_id, operation, attempt }`, plus summary counters. The sweep catches individual
   dictionary and reconcile errors with `console.error()` and continues, so the scheduler's
   top-level `cron_run_failed` cannot see those swallowed failures.

4. **Server boot marker.**
   `hooks.server.ts` → `server_started` → `info`, with
   `{ app_version, commit, container, is_standby }`. There is still no boot event; this review had
   to infer deploy boundaries from client build first-seen and Caddy logs.

5. **Raw-fetch failure breadcrumb.**
   `remote-log.ts`/the raw-fetch boundary → `fetch_failed` breadcrumb or handled warning with
   `{ method, pathname, age_ms }`. Shared `post_request`/`get_request` failures already name their
   routes; this is only for the otherwise bare `Failed to fetch` family and should remain bounded.

6. **Saved-message follow-up delivery.**
   `messages/contact/+server.ts` → `contact_followup_delivery_failed` → `warn`, with
   `{ subject_key, dictionary_id, recipient_class, recipient_count }` and no personal data.
   The thread save can succeed while a targeted manager/partner follow-up email is caught only by
   `console.error`.

7. **Remove duplicate bundle emission.**
   `entries-ui-store.ts` → keep one structured `dict_bundle_read_failed` error carrying
   `{ attempts, final_state }`; do not emit both patched `console.error` and `log_event`.

Coverage already present and therefore **not proposed again**: authentication send/verify, upload
and photo upload, dictionary creation/catalog/invite, sync push success and failure, v1 bulk writes,
inbound email and replies, analytics child jobs, media sweeps, WAL checkpoints, and top-level cron
failures.

### 🟠 P2 — a signed-in contributor was locked out of a private dictionary by a deleted script file

On July 29 between 22:29 and 22:35 UTC, a signed-in contributor opened the **private `algonquin`
dictionary** and the browser could not load the worker JavaScript file
`/_app/immutable/workers/chunks/DASUsDk6.js` — a file belonging to an older build that a deploy had
already removed from the server. The consequences, read straight from that one session:

| What was logged | Count |
|---|---:|
| `leader_boot_failed` (retrying) | 39 |
| `dict_boot_recovery_exhausted` (gave up) | 14 |
| `initial dict sync failed` — "RPC timed out (no leader responded)" | 1 |
| `Failed to read dict bundle from wa-sqlite` | 2 |
| Time to First Byte on the page reload | 9,989 ms (rated "poor") |

The retry loop is hopeless by construction: the file it wants no longer exists on the server, so no
number of retries can succeed. The only cure is a page reload onto the current build.

**The application already knows how to do exactly this in a neighbouring case.** Earlier the same
day (14:29 UTC) the same person hit a `schema_outdated` sync rejection and the app emitted
`schema_outdated_reload` and reloaded itself, and she carried on working. The recommendation is to
classify a boot failure whose message matches the module-loading family ("error loading dynamically
imported module", "Failed to fetch dynamically imported module", "Importing a module script
failed.") as a **stale bundle**, and give it the same single, one-shot reload.

<Callout type="warn" title="This is deliberately NOT the zombie-tab ruling">
The standing decision of 2026-07-09 says no forced-reload mechanism will be built for stale
background tabs producing sync-failure storms. That ruling is about forgotten background tabs
belonging to nobody's active work. This is different in every dimension that matters: a foreground
tab, a signed-in contributor, her own private dictionary, a load that can never succeed, and a
reload path that already exists in the codebase for the sibling case.
</Callout>

Across the whole window the module-loading boot-failure family was 11 rows over 4 sessions today,
against 64 rows over 9 sessions on July 29 — small, but it lands on real editors.

sheds, so Cloudflare's edge could cache almost nothing and the same scrapers returned every minute —
the shedding fed itself. With the bigger store, responses became cacheable and the loop broke.
