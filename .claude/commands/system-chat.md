# Post as System into a chat room

Jacob wants a message posted into an LD chat room authored by **System** (not
"Jacob"), so the other people know it's Jacob's agent — but it still lands in the
normal thread so the conversation continues. Members get their usual ping (email/
ntfy), except Jacob himself.

**How it works:** you POST to a **loopback-only** endpoint on the box,
`/api/internal/system-chat`, which posts the message as the System bot (it doesn't
need to be a room member) and fires the normal member notification, skipping the
`skip_user_id` you set (Jacob). Delivery is SYNCHRONOUS — a 200 means posted and
notified; any other status is a real error with a reason, so there is nothing to
poll. See `$lib/server/chat/system-message.ts`.

> Replaced the old `chat_system_outbox` + 20s drain cron (2026-07-29). The table
> still exists but is unused and unwritten — dropping it would need a shared
> migration, which throws `CLIENT_BEHIND` at every user until they reload.

**Auth:** two gates, both fail closed — an `x-internal-token` header matching
`/opt/hosting/data/.internal-api-token` (generated by the app on first boot; only
readable as root on the box), and a refusal to serve any request carrying proxy
headers, so the route is unusable from the public internet even with the token.

## What Jacob gives you
- **Which room** — usually "my DM with Greg", "the Diego/Greg/me room", or a
  channel name.
- **What to say** — the message text.

## Steps

### 1. Pick the target

| | shared.db path (for the read-only lookups) | post to |
|---|---|---|
| **prod** (default) | `/opt/hosting/data/shared.db` | `http://127.0.0.1:3001/api/internal/system-chat` on the box |
| **dev** | `site/.data/shared.db` | `http://localhost:5173/api/internal/system-chat` |

> **Dev:** the token is at `site/.data/.internal-api-token`. Nothing is dormant in
> dev any more — the endpoint works exactly as it does in prod.

For the read-only lookups in step 2, write the script to `/tmp/q.js` and pipe it
via stdin — escaping inside `docker exec` is brutal (see the database skill).

### 2. Resolve the room id + recipients (read-only first)

Run this to find the room and confirm who'll be pinged. Adjust the email filter to
the people Jacob named:

```js
const db = require('better-sqlite3')('/data/shared.db', { readonly: true })
// Rooms Greg is in, with their members — find the one Jacob means:
const rooms = db.prepare(`
  SELECT r.id, r.kind, r.name,
    (SELECT group_concat(u.email, ', ') FROM chat_room_members m JOIN users u ON u.id = m.user_id WHERE m.room_id = r.id) AS members
  FROM chat_rooms r
  WHERE r.id IN (SELECT room_id FROM chat_room_members m JOIN users u ON u.id = m.user_id WHERE u.email = 'livingtongues@gmail.com')
`).all()
console.log(JSON.stringify(rooms, null, 2))
// Jacob's user id (to skip pinging him):
console.log(db.prepare(`SELECT id FROM users WHERE email = 'jwrunner7@gmail.com'`).get())
```

Notes:
- A **DM** room id is `dm:` + the two user ids sorted + joined by `:`
  (`dm_room_id` in chat-db.ts). Group rooms have their own ids/names
  (e.g. `diego-greg-jacob`). Just take the `id` from the query above.
- Greg = `livingtongues@gmail.com`, Diego = `diego@livingtongues.org`,
  Anna = `dictionaries@livingtongues.org`, Jacob = `jwrunner7@gmail.com`.
- **Echo the room + member emails back to Jacob and get his OK before writing** —
  this pings real people.

### 3. Post the message

`body_html` renders as trusted HTML in the chat (it's sanitized again on post) —
keep it simple (`<p>…</p>`, escape anything from Jacob's input). `body_text` is the
plain-text mirror used for previews + the ping. `skip_user_id` = Jacob's id so he
isn't pinged for his own agent's message.

Write the JSON to a file first — quoting a nested payload through `ssh` is the
usual way this goes wrong.

```bash
cat > /tmp/msg.json <<'JSON'
{
  "room_id": "ROOM_ID",
  "body_html": "<p>…</p>",
  "body_text": "…",
  "skip_user_id": "JACOB_USER_ID"
}
JSON
scp /tmp/msg.json living:/tmp/msg.json
ssh living 'sudo curl -sS -o /tmp/out.json -w "%{http_code}\n" \
  -X POST http://127.0.0.1:3001/api/internal/system-chat \
  -H "content-type: application/json" \
  -H "x-internal-token: $(sudo cat /opt/hosting/data/.internal-api-token)" \
  --data-binary @/tmp/msg.json; cat /tmp/out.json'
```

### 4. Read the result — there is nothing to poll

- **200** + `{"ok":true,"message_id":"…"}` → posted and everyone notified. Done.
- **400** → your payload was wrong (missing field / bad JSON). Fix and retry.
- **404** → the token or the loopback gate rejected you. You are either not on the
  box, went through Caddy (use `127.0.0.1:3001`, not the public domain), or read
  the token file wrong.
- **500** → delivery genuinely failed; the body carries the reason (e.g.
  `room not found: …`). Report it to Jacob.
